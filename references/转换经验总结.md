## 一、任务概述

### 输入
- **LaTeX 论文源**：`latex模板/` — 4章正文 + 摘要 + 参考文献 + 封面信息
- **Word 模板**：`agent用模板.xml`（Flat OPC XML，73个part，15个节，24个页眉，9个页脚）

### 输出
- `thesis_output.docx`（4.8 MB）— 可直接用 Word 打开的论文 DOCX
- `thesis_output.xml`（8 MB）— Flat OPC XML 源文件

## 三、关键问题与修复（全记录）

### 第一波：基本可打开

#### 🚨 Q1: `[Content_Types].xml` 缺失
- **现象**：DOCX 在 Word 中无法打开
- **根因**：Flat OPC XML 中 `[Content_Types].xml` 以隐式方式存在，转换时丢失
- **修复**：改为以原始 `.docx` 为基底，仅替换 `word/document.xml`，追加新 part

#### 🚨 Q2: 图片 ZIP 路径错误
- **现象**：图片被写入 `media/file.png` 而非 `word/media/file.png`
- **根因**：`writestr(img_arc, ...)` 直接使用关系文件中的相对路径
- **修复**：路径前加 `word/` 前缀

#### 🚨 Q3: LaTeX 命令残留在正文
- **现象**：段落中出现 `\section{标题}` 纯文本
- **根因**：章节分割用 `m.start()` 而非 `m.end()`
- **修复**：`last_end = m.end()`

#### 🚨 Q4: 标题级别错误
- **现象**：节标题全部使用H1样式
- **根因**：JSON level 直接映射为样式ID
- **修复**：`h_level = min(sec_level + 1, 3)`

#### 🚨 Q5-Q6: 命名空间问题
- 293处冗余 `xmlns:w` → `fix_docx.py` 剥离子元素命名空间
- `xmlns:a`/`xmlns:pic` 缺失 → 注入根元素

#### 🚨 Q7: 缺少 jpg Content_Type
- 模板只有 png，没有 jpg 注册
- 修复：`fix_docx.py` 自动检测并添加

#### 🚨 Q8: rId 不一致（最隐蔽）
- 正文用 rId101-113，rels 注册 rId201-213
- 根因：两个独立函数使用不同 rId 序列
- 修复：统一使用 `get_image_rel_id._cache`

#### 🔴 Q9: 孤立 `<w:r>` 无 `<w:p>` 包裹
- 所有图片 `<w:r><w:drawing>` 直接挂在 `<w:body>` 下
- OOXML 规范禁止 `<w:r>` 作为 `<w:body>` 直接子元素
- 修复：`make_image_tag()` 返回 `<w:p>` 包裹版本

### 第二波：排版精细化

#### 🎯 Q10: 引用上角标
- 模板引用显示为普通文本，需要上标
- `ooxml_generator.py` 增加 `_CITATION_RE` 正则匹配 `[N]`/`[N,M]`/`[N-M]`
- 自动拆分为独立 `<w:r>`，加 `<w:vertAlign>superscript</w:vertAlign>` + 9pt字号
- 最终：38处上标引用

#### 🎯 Q11: 标题 Run 级格式覆盖
- H1: 不加粗(`w:b w:val="0"`)、32pt(16pt)、黑体、居中、line=480(2.0x)
- H2: 不加粗、24pt(12pt)、两端对齐、黑体、line=360(1.5x)、段前段后156
- H3: 加粗、24pt(12pt)、黑体、左对齐、line=360(1.5x)、style "3"
- 模板注释明确："三级=style3"

#### 🎯 Q12: 正文段落显式格式
- `make_body_paragraph()` 现在显式指定：
  - `firstLine="480"`（首行缩进2字符）
  - `sz="24"`（12pt五号字）
  - `spacing line="360" lineRule="auto"`（1.5倍行距）
- 结论/致谢段落同样处理

#### 🎯 Q13: 分页符
- 章间插入 `<w:br w:type="page"/>`，替换原先的 `pass`

#### 🎯 Q14: `&amp;lt;` 双重转义修复
- `&amp;lt;` 显示为 `&lt;` 而不是 `<`
- `fix_docx.py` 后处理：`&amp;lt;`→`&lt;`，`&amp;gt;`→`&gt;`，`&amp;amp;`→`&amp;`
- 7处降为0

#### 🎯 Q15: LaTeX残留清理（`clean_inline_latex`）
- 嵌套花括号 `\bm{X}` 的处理：`\$((?:[^{}]|\{[^}]*\})*)\$`
- 40+种 LaTeX 命令转换（箭头/运算符/希腊字母/字体命令）
- 迭代5层深度清理
- HTML实体迭代3次解嵌套
- `\ref` 模式保留供后续 REF 域替换
- 末尾 `\\[a-zA-Z]+` 兜底清除无法识别的残留命令

### 第三波：特性增强

#### 🚀 Q16: 标题自动编号（numbering.xml）
- 注入 abstractNum(100) + num(100) 到 numbering.xml
- H1/H2/H3 通过 `<w:numPr>` 引用自动编号
- 标题文本不再包含手动编号前缀

#### 🚀 Q17: TOC 域代码 + settings.xml updateFields
- settings.xml 添加 `<w:updateFields w:val="true"/>`
- Word 打开文档时自动更新所有域（目录、页码、交叉引用）

#### 🚀 Q18: 图片等比缩放（PIL）
- `get_image_dimensions()` 读取图片真实尺寸
- 按页面宽度等比缩放（默认最大宽度 5040000 EMU ≈ 14cm）
- 保持宽高比，避免图片拉伸变形

#### 🚀 Q19: 交叉引用书签 + REF域
- 图题插入 `<w:bookmarkStart/>` + `<w:bookmarkEnd/>`
- 正文 `\ref{fig:xxx}` 替换为 REF 域代码（`REF _Fig_ch1_1 \r \h`）
- ref_map 自动构建（扫描所有 figure/table 的 label）
- 未解析的 ref 显示 `[label]` 作为 fallback

#### 🚀 Q20: LaTeX 引号修复
- ` `` ` → Unicode 左双引号 `\u201c`
- ` '' ` → Unicode 右双引号 `\u201d`
- 修复表格 `\textbf{...}`、`\textit{...}` 等残留命令

## 五、经验教训

### 5.1 Flat OPC XML 的陷阱

1. **命名空间声明方式不同**：每个子元素可能携带完整声明，打包为 DOCX 时必须剥离至根元素
2. **`[Content_Types].xml` 隐式存在**：需从原始 .docx 继承
3. **rId 空间不连续**：模板 rId 与生成 rId 需统一管理

### 5.2 验证工具的选择

| 工具 | 检测能力 | 不足 |
|------|----------|------|
| `xml.etree.ElementTree` | XML 格式、命名空间 | 不验证 OOXML 模式 |
| `python-docx` | 部分 OOXML 结构 | 不验证强制元素顺序（如 `<w:p>` 必须包裹 `<w:r>`） |
| **Word 本身** | **完整 OOXML 模式验证** | 错误信息不详细，需反复试错 |
| `lxml` schema 验证 | OOXML 模式完整验证 | 需要 XSD 文件 |

**关键经验**：python-docx 能打开 ≠ Word 能打开。python-docx 是惰性验证，Word 是严格模式验证。最终必须用 Word 实际打开测试。

### 5.3 最隐蔽的问题排名

| 排名 | 问题 | 发现耗时 | 为什么隐蔽 |
|------|------|---------|-----------|
| 1 | **孤立 `<w:r>` 无 `<w:p>` 包裹** | ~2小时 | python-docx 不检查此模式违反，Word 严格拒绝 |
| 2 | **rId 不一致** | ~1.5小时 | 两个函数独立产生 rId，debug 时难以察觉 |
| 3 | **命名空间泛滥** | ~1小时 | 外观正常、XML 语法正确，但 Word 拒绝 |
| 4 | **`&amp;lt;` 双重转义** | ~30分钟 | 文本内容正确但经过两次 XML 序列化 |
| 5 | **行距继承链断裂** | ~20分钟 | style 定义中无 spacing，导致单倍行距 |

### 5.4 文本替换 vs XML 结构替换

封面等复杂区域（含表格、多 run 拆分字符）不适合文本替换：
- 中文字符可能跨多个 `<w:t>` 元素（如"王"和"伟"在不同 run 中）
- 文本替换可能命中非目标区域
- 空格和格式字符在 XML 中不可见

**推荐做法**：使用 python-docx API 或生成完整 OOXML 片段替换整个区间。

### 5.5 clean_inline_latex 的演进

```
v1: 简单替换 $...$ → 基础符号转换
v2: 非贪心 .*? 匹配 → 希腊字母/命令处理
v3: 嵌套花括号 ((?:[^{}]|\{[^}]*\})*) → 迭代5层深度清理
v4: \ref{...} 保留 → HTML实体迭代解嵌套 → \\[a-zA-Z]+ 兜底
```

### 5.6 推荐架构

```
1. 解析层: LaTeX → 结构化 JSON（已有 latex_parser.py）
2. 生成层: JSON → OOXML 片段（已有 ooxml_generator.py）
3. 组装层: 基于 python-docx API 组装（避免 Flat OPC 陷阱）
4. 后处理层: 命名空间修复 + rId 对齐 + Content_Types 补全
```

## 八、工作流深层反思：为什么AI没有直接操作XML？

### 8.1 代码编辑 vs OOXML编辑的范式鸿沟

第一轮迭代最值得追问的一个问题：**AI修改代码时可以直接定位到文件+行号做精确替换，为什么面对XML却选择写Python脚本来生成？** 不是不能识别XML，而是OOXML不适合"单文件字符串编辑"模式。

| 维度 | 代码文件（.py/.ts） | OOXML Flat OPC（.xml） |
|------|-------------------|----------------------|
| **单文件自洽性** | 一个编译单元自洽，改一行就生效 | 涉及 4+ 个关联文件的同步修改（document.xml, styles.xml, numbering.xml, rels, Content_Types） |
| **结构容错性** | 语法错误→编译器精确报错，不破坏其他代码 | 一个 `<w:r>` 缺少 `<w:p>` 包裹→整个文档打不开，错误信息毫无帮助 |
| **训练数据密度** | GitHub上百亿行代码，AI对代码模式极度熟悉 | OOXML内部结构训练数据极少，AI"凭感觉"生成 |
| **增量编辑可行性** | `edit` 工具精确替换5行，边界清晰 | OOXML的一个段落跨10+行，嵌套层级深，精确匹配oldString困难 |
| **验证反馈速度** | LSP/编译器秒级报错 | 修改→ZIP打包→Word打开→报错，一个周期2-5分钟 |
| **命名空间** | 没有（或import级别处理） | 多个ns（w:, a:, r:, pic:, m:），声明位置有严格约束，子元素携带声明会导致Docx打不开 |

**核心结论**：代码修改是"在已知位置做局部替换，上下文自洽"；OOXML修改是"跨多个ZIP内部文件做原子性同步修改，上下文耦合"。AI选择写Python作为中间层是**正确的工程决策**——代码层隔离了OOXML的复杂性，把问题从"改XML字符串"降维为"调Python API"。

### 8.2 直接字符串操作XML导致的所有隐蔽bug

回顾第三波记录，排名前5的最隐蔽问题**全部源于"字符串拼接XML"而非结构化API操作**：

| 排名 | Bug | 为什么字符串拼接会导致它 | 用python-docx API能否避免 |
|------|-----|----------------------|--------------------------|
| 1 | 孤立 `<w:r>` 无 `<w:p>` 包裹 | f-string 生成 `<w:r>` 片段时未检查父元素上下文 | ✅ `doc.add_paragraph()` 自动包裹 |
| 2 | rId 不一致 | 两个函数独立维护计数器，无全局状态 | ✅ `doc.add_picture()` 自动分配rId |
| 3 | 命名空间泛滥 | `xml.etree.register_namespace` 导致每个子元素挂声明 | ✅ python-docx 内部管理 |
| 4 | `&amp;lt;` 双重转义 | 文本先被HTML转义，再被XML序列化二次转义 | ✅ 直接设置 `run.text` 不经过两层 |
| 5 | 行距继承链断裂 | 改了`document.xml`但没同步改`styles.xml` | ✅ `paragraph.style = doc.styles['aa']` |

### 8.3 `.txt` 扩展名方案的无效性

一个顺理成章的猜想：如果把Flat OPC XML保存为`.txt`，AI工具会不会更容易编辑？答案：**不会，扩展名换不来任何实质改进。**

- **AI工具对文件类型的处理**：如果上一轮使用的AI工具有`.xml`限制，那只是工具层面的问题。but 真正的瓶颈不在文件扩展名，而在于OOXML本身的跨文件耦合。
- **Word打开行为**：Word能打开Flat OPC XML（`.xml`），但无法识别`.txt`。你需要手动改扩展名，反而增加了人工步骤。
- **8MB文件大小**：任何AI模型的单次上下文都处理不了4000+行的OOXML。无论是`.txt`还是`.xml`，都需要分块操作——这与扩展名无关。

## 九、下一代工作流方案（v2）

### 9.1 核心原则

> **不再直接拼接OOXML字符串。让专用工具处理各自擅长的事。**

- pandoc 擅长：LaTeX → OMML 公式转换（这是v1最大的缺失）
- python-docx 擅长：OPC/ZIP打包、样式API、rId管理、Content_Types自动化
- 自己的解析器擅长：LaTeX结构化提取（`latex_parser.py` 做章节/引用/图表/元数据的JSON化）

### 9.2 新架构

```
LaTeX .tex
    │
    ├─→ pandoc -o interim.docx              ← pandoc处理公式，生成OMML
    │       │
    │       └─→ 提取OMML片段 (m:oMath/...)
    │
    └─→ latex_parser.py → thesis_content.json  ← 保留现有解析逻辑
            │
            ├─ metadata (作者/学校/专业/日期)
            ├─ chapters[4]
            ├─ conclusion + acknowledgement
            └─ references[34]
            │
            ▼
    python-docx 组装层 (新建 generate_v2.py)
            │
            ├─ doc = Document('agent用模板.docx')  ← 从真实模板启动
            ├─ for each chapter:
            │   ├─ add_heading(title, level=1)       ← 自动映射样式
            │   ├─ 公式：注入pandoc产生的OMML片段
            │   ├─ 正文：add_paragraph(text, style='aa')
            │   ├─ 引用上标：run.font.superscript=True (一行搞定)
            │   ├─ 图片：doc.add_picture()            ← 自动管理rId/rels
            │   └─ 图题：add_paragraph(caption, style='a6')
            │
            ▼
    final.docx
```

### 9.3 各层对比：v1 vs v2

| 层次 | v1（第一轮） | v2（建议） | 为什么改 |
|------|------------|-----------|---------|
| **公式** | `clean_inline_latex()` 正则→纯文本 | pandoc → OMML片段注入 | v1的40+种LaTeX命令转换不可能穷尽；v2借力pandoc的成熟引擎 |
| **文档组装** | f-string拼接XML + `fix_docx.py`后处理 | `python-docx` API | v1触发了5个隐蔽bug；v2 API层自动处理这些 |
| **样式映射** | 手动指定style ID字符串 | `doc.styles['aa']` 对象 | v2的样式对象可直接读写属性，不会遗漏行距等 |
| **图片** | 手动Base64+rels+rId管理 | `doc.add_picture()` | v1的rId不一致bug直接消失 |
| **引用上标** | `_CITATION_RE.split()` + 拼`<w:vertAlign>` | `run.font.superscript = True` | 一行Python替代30行正则+XML拼接 |
| **标题编号** | 手动f-string拼`"1 绪论"` | numbering.xml注入 + `<w:numPr>` | v2自动编号，支持Word中动态更新 |
| **LaTeX解析** | `latex_parser.py` → JSON | **保留不变** | 这层没问题 |

### 9.4 各问题的修复路径对照

| 问题 | v1状态 | v2修复方式 | 难度 |
|------|--------|----------|------|
| 公式纯文本 | `clean_inline_latex()` 正则替换不完整 | pandoc 生成 OMML → 从 interim.docx 提取 → 注入 python-docx | 中 |
| 引用不上标 | `_CITATION_RE` 未触发 | `run.font.superscript = True`（python-docx一行） | 低 |
| 二级/三级标题格式 | `make_heading()` 只设style ID，无run级覆盖 | 读取模板中对应样式的`<w:rPr>`属性，通过python-docx显式设置 | 中 |
| 目录不自动更新 | 静态TOC文本 | 插入TOC域代码 + `settings.xml` 设 `updateFields=true` | 低 |
| 分页缺失 | `if ch_num: pass` | `doc.add_page_break()` 每章之间 | 低 |
| 行距继承断裂 | style "aa" 无 spacing 定义 | python-docx 显式设置 `paragraph_format.line_spacing = 1.5` | 低 |
| 页眉页脚 | sectPr继承部分丢失 | 从模板复制完整sectPr，python-docx逐section设置 | 中 |

### 9.5 风险与限制

| 风险 | 说明 | 缓解 |
|------|------|------|
| pandoc OMML质量 | pandoc的LaTeX→OMML并非完美，复杂公式（矩阵、多行对齐）可能失真 | 对关键公式做手工验证，不理想的用MathType补救 |
| python-docx对OMML支持 | python-docx原生不直接支持`m:oMath`操作 | 通过`lxml`在paragraph的XML层面注入OMML片段（可控的局部XML操作） |
| 模板样式继承 | 模板中style "3"定义不完整（正文从未使用），直接映射可能出错 | 先审计模板styles.xml，补全定义，再做映射 |
| 跨章节编号重置 | numbering.xml的`w:start`控制每章从1开始 | 需在每章`sectPr`中处理，可能需要手动调整 |

## 十一、temp_main.xml 格式参考——真实 Word 文档的 OMML/目录/标题模板

> `temp_main.xml`（2.7MB Flat OPC XML）是一份中文理工科论文，由 Word 原生生成，包含 **93个内联公式**（`m:oMath`）、**33个显示公式**（`m:oMathPara`）、完整的 TOC 域代码链路，是 v2 工作流的**格式参考金标准**。

### 11.1 OMML 元素全景

| 元素 | 数量 | 用途 |
|------|------|------|
| `m:oMath` | 93 | 内联公式容器（嵌在正文段落中） |
| `m:oMathPara` | 33 | 显示公式段落容器（独立段落、居中） |
| `m:sSub` | 192 | 下标（如 $x_1$） |
| `m:sSup` | 12 | 上标（如 $R^n$） |
| `m:f` | 2 | 分式（如 $1/N$） |
| `m:nary` | 14 | 大型运算符（求和/积分） |
| `m:eqArr` | 24 | 方程组/多行对齐 |
| `m:func` / `m:fName` | 2 | 函数名（如 max） |
| `m:limLow` | 2 | 下极限（如 $\max_{0 \le t \le T}$） |
| `m:e` | 123 | 子表达式参数容器 |
| `m:ctrlPr` | 170 | 字体控制属性包裹器 |
| **缺失项** | **0** | `m:rad`（根号）、`m:acc`（重音）、`m:bar`、`m:d`（定界符）——该论文恰好未使用 |

**关键规则**：
- 所有公式文本使用 `Cambria Math` 字体，`sz=24`（12pt）
- 每个属性元素（`m:sSubPr`/`m:sSupPr`/`m:fPr` 等）内部必须包裹 `m:ctrlPr → w:rPr` 以指定字体
- 公式编号用 `m:sty m:val="p"` 标记为普通文本样式（`#(2.1)` 中的括号和编号）

### 11.2 五种核心 OMML 模板（可直接复用为 Python 字符串模板）

#### 模板 A：内联下标（$x_1, x_2, ..., x_n$）

```xml
<m:oMath>
  <m:r>
    <w:rPr><w:rFonts w:ascii="Cambria Math" w:hAnsi="Cambria Math"/><w:sz w:val="24"/></w:rPr>
    <m:t>X=(</m:t>
  </m:r>
  <m:sSub>
    <m:sSubPr><m:ctrlPr><w:rPr><w:rFonts w:ascii="Cambria Math" w:hAnsi="Cambria Math"/><w:sz w:val="24"/></w:rPr></m:ctrlPr></m:sSubPr>
    <m:e><m:r><w:rPr>...Cambria Math, sz=24...</w:rPr><m:t>x</m:t></m:r></m:e>
    <m:sub><m:r><w:rPr>...</w:rPr><m:t>1</m:t></m:r></m:sub>
  </m:sSub>
  <m:r><m:t>,</m:t></m:r>
  <!-- 重复 m:sSub 模式 x2 ... xn -->
  <m:r><m:t>)</m:t></m:r>
</m:oMath>
```

#### 模板 B：显示公式 + 公式编号（居中，序号右对齐）

```xml
<m:oMathPara>
  <m:oMath>
    <m:eqArr>
      <m:eqArrPr>
        <m:maxDist m:val="1"/>
        <m:ctrlPr><w:rPr><w:rFonts w:ascii="Cambria Math" w:hAnsi="Cambria Math"/><w:sz w:val="24"/></w:rPr></m:ctrlPr>
      </m:eqArrPr>
      <m:e>
        <m:r><m:t>θ=f(X)</m:t></m:r>
        <m:r><m:rPr><m:sty m:val="p"/></m:rPr><m:t>#(2.1)</m:t></m:r>
      </m:e>
    </m:eqArr>
  </m:oMath>
</m:oMathPara>
```

**关键**：`m:oMathPara` 必须放在独立的 `<w:p>` 段落中，不能与正文混合。

#### 模板 C：分式（$\frac{1}{N}$, $\frac{N_f}{N}$）

```xml
<m:f>
  <m:fPr><m:ctrlPr><w:rPr>...Cambria Math, sz=24...</w:rPr></m:ctrlPr></m:fPr>
  <m:num><m:r><m:t>1</m:t></m:r></m:num>
  <m:den><m:r><m:t>N</m:t></m:r></m:den>
</m:f>
```

#### 模板 D：上标（$R^n$）

```xml
<m:sSup>
  <m:sSupPr><m:ctrlPr><w:rPr>...</w:rPr></m:ctrlPr></m:sSupPr>
  <m:e><m:r><m:t>R</m:t></m:r></m:e>
  <m:sup><m:r><m:t>n</m:t></m:r></m:sup>
</m:sSup>
```

#### 模板 E：函数 + 下极限（$\max_{0\le t\le T}$）

```xml
<m:func>
  <m:funcPr><m:ctrlPr>...</m:ctrlPr></m:funcPr>
  <m:fName>
    <m:limLow>
      <m:e><m:r><m:rPr><m:sty m:val="p"/></m:rPr><m:t>max</m:t></m:r></m:e>
      <m:lim><m:r><m:t>0≤t≤T</m:t></m:r></m:lim>
    </m:limLow>
  </m:fName>
  <m:e><!-- 函数参数 --></m:e>
</m:func>
```

**注意**：该论文中不存在 `m:rad`（根号）、`m:acc`（重音）——如果你的 LaTeX 源包含 `\sqrt{}`、`\bar{}` 等，需从 Word 手工生成一个含这些元素的 .docx 再提取模板。

### 11.3 目录（TOC）的完整链路

temp_main.xml 揭示了 TOC 的三个联动环节：

#### 环节 1：标题样式定义中的 `outlineLvl`

```
styleId="1" (heading 1) → outlineLvl="0" → TOC一级
styleId="2" (heading 2) → outlineLvl="1" → TOC二级
styleId="3" (heading 3) → outlineLvl="2" → TOC三级
```

#### 环节 2：正文标题中的书签

每个标题段落同时携带 `<w:bookmarkStart w:name="_TocXXXXX"/>`，作为 TOC 超链接的目标锚点。

#### 环节 3：TOC 域代码 + PAGEREF

```xml
<w:p><w:pPr><w:pStyle w:val="TOC3"/></w:pPr>
  <w:r><w:fldChar w:fldCharType="begin"/></w:r>
  <w:r><w:instrText xml:space="preserve"> TOC \o "1-3" \h \z \u </w:instrText></w:r>
  <w:r><w:fldChar w:fldCharType="separate"/></w:r>
  <!-- 每个条目：超链接 + PAGEREF 域 -->
  <w:hyperlink w:anchor="_Toc21882">
    <w:r><w:t>1  研究目标与内容</w:t></w:r>
    <w:r><w:tab/></w:r>
    <w:r><w:fldChar w:fldCharType="begin"/></w:r>
    <w:r><w:instrText> PAGEREF _Toc21882 \h </w:instrText></w:r>
    <w:r><w:fldChar w:fldCharType="end"/></w:r>
  </w:hyperlink>
  <!-- ... -->
  <w:r><w:fldChar w:fldCharType="end"/></w:r>
</w:p>
```

**关键参数**：`TOC \o "1-3" \h \z \u`
- `\o "1-3"`：基于 outlineLvl 0-2 构建目录
- `\h`：生成超链接（Ctrl+点击跳转）
- `\z`：Web 布局中隐藏制表符前导符
- `\u`：使用段落大纲级别

**v2 策略**：用动态 TOC（仅域代码 + `updateFields=true`），让 Word 打开时自动填充，无需手动生成 PAGEREF 条目。

### 12.2 五个问题的根因与修复

#### 🚨 Q21: TOC回退为模板静态目录
- **现象**：目录是模板遗留的静态条目（手工点线+手工页码），无法在Word中更新
- **根因**：`replace_body_content()` 函数从未处理TOC区域（markers[6]到markers[8]之间的内容）
- **修复**：在 `replace_body_content()` 中新增TOC处理步骤，用动态域代码替换静态条目：
  ```xml
  <w:instrText xml:space="preserve"> TOC \o "1-3" \h \z \u </w:instrText>
  ```
- **关键**：反斜杠必须为单反斜杠（`\o` 而非 `\\o`），使用 `chr(92)` 拼接

#### 🚨 Q22: 公式编号不右对齐且含重复编号
- **现象**：编号出现在公式末尾而非右对齐；同一编号出现多次
- **根因**：
  1. `make_equation_omml_paragraph()` 传入 `eq_number=None`，绕过了OMML内部编号机制，改用tab+独立run的方式附加编号
  2. `parse_content_blocks()` 中 `eq_counter = [0]` 在每个section重置，导致跨section的重复编号
- **修复**：
  1. 将 `eq_number=None` 改为 `eq_number=eq_number`，让编号嵌入OMML内部的 `<m:eqArr>`
  2. 在 `generate_main_body()` 中维护每章的方程计数器 `eq_counter`
  3. 编号前加 `#` 前缀（`<m:t>#(2-1)</m:t>`），使用 `m:sty m:val="p"` 纯文本样式

#### 🚨 Q23: 内联公式（$...$）未转换为OMML
- **现象**：正文中的 `$\theta$` 等被渲染为纯文本 `\theta`（Cambria Math字体），而非可编辑公式
- **根因**：
  1. `make_body_paragraph_with_math()` 的 `fromstring()` 解析OMML时，wrapper只声明了 `xmlns:m`，缺少 `xmlns:w` 命名空间声明（因为OMML内部使用了 `w:rPr`、`w:rFonts` 等w:前缀元素）
  2. `latex_to_omath()` 返回空字符串时，数学内容被静默丢弃
- **修复**：
  1. 添加 `xmlns:w="{NS_W}"` 到 `fromstring()` 的wrapper fragment
  2. 新增 `_fallback_math_to_unicode()` 函数，在OMML解析失败时将LaTeX转为Unicode符号

### 12.3 关键发现：内联OMML的namespace陷阱

```python
# ❌ 失败：缺少xmlns:w声明
fragment = fromstring(f'<frag xmlns:m="...">{omml}</frag>')

# ✅ 正确：必须同时声明w命名空间
fragment = fromstring(f'<frag xmlns:m="..." xmlns:w="...">{omml}</frag>')
```

因为 `latex_to_omath()` 在内联公式中使用了 `w:rPr` 元素（字体设置），这些元素需要 `w:` 命名空间。如果没有声明，`fromstring()` 会抛出XML解析异常，导致回退到纯文本模式。这是内联OMML一直等于0的根本原因。

### 12.4 关键发现：三线表正确实现

```python
# ❌ 错误：insideH会在所有数据行之间产生横线
tblBorders: top(sz=12), bottom(sz=12), insideH(sz=4)

# ✅ 正确：表头行下方用tcBorders
tblBorders: top(sz=12), bottom(sz=12)
# 表头单元格上：tcPr > tcBorders > bottom(sz=4)
```

`insideH` 在OOXML中会在所有相邻行之间产生横线——不仅表头到数据之间，数据行之间也有。正确做法是只在表头单元格上加下边框。

### 12.5 关键发现：TOC样式定义

OOXML中TOC由 `TOC \o "1-3" \h \z \u` 域代码驱动，但生成的条目使用TOC1/TOC2/TOC3样式。这些样式如果未在styles.xml中定义，Word会使用内置默认值（从Normal继承9pt字号）。

```xml
<w:style w:type="paragraph" w:styleId="TOC1">
  <w:name w:val="toc 1"/>
  <w:basedOn w:val="a"/>
  <w:pPr>
    <w:ind w:left="397"/>
    <w:tabs><w:tab w:val="right" w:leader="dot" w:pos="9071"/></w:tabs>
  </w:pPr>
  <w:rPr><w:sz w:val="24"/><w:szCs w:val="24"/></w:rPr>
</w:style>
```

**必须显式定义**TOC1/TOC2/TOC3样式，包括字号(12pt)、制表位(9071 twips)和点前导符。

### 12.6 关键发现：XML解析失败的排查顺序

当Word无法打开Flat OPC XML时，按以下顺序排查：

1. **lxml.fromstring() 全文件解析** — 最直接的XML良构性检查
2. **查找重复闭合标签** — `</w:p></w:p>`、`</w:r></w:r>` 等重复模式
3. **检查 `<w:document>` 和 `<w:body>` 开闭平衡**
4. **检查 `<`/`>` 数量差异** — 多余的`>`可能来自文本内容中的未转义字符
5. **检查 `m:oMathPara` 是否在 `<w:r>` 内部** — 显示公式不应在run中
6. **检查命名空间声明完整性**

### 13.3 关键发现：模板自带的标签错位

#### 发现 1：`<w:t>text</w:r>`（10处）
模板中部分 `<w:t>` 元素以 `</w:r>` 结尾而非 `</w:t>`。这是最隐蔽的错误：计数分析显示 `w:t: 890/880 (diff=10)` 但直接搜索 `</w:t>` 找不到缺失。

**文本级修复**：
```python
for m in re.finditer(r'<w:t[\s>]', body):
    te = m.end()
    nr = body.find('</w:r>', te)
    nt = body.find('</w:t>', te)
    if nr >= 0 and (nt < 0 or nr < nt) and '<' not in body[te:nr]:
        body = body[:nr] + '</w:t>' + body[nr+6:]
```

#### 发现 2：游离 `</w:r>` 在 VML textbox 外（1处）
```xml
</mc:Fallback></mc:AlternateContent></w:r></w:p>
```
`</w:r>` 出现在 `</mc:AlternateContent>` 和 `</w:p>` 之间，而此处没有对应的 `<w:r>` 开启。导致 lxml 报 `"p closed by r"`。

**修复**：线性扫描找到 balance 首次为负的位置，移除该 `</w:r>`。

#### 发现 3：`<w:p>` 嵌套在 `<w:r>` 内部
在 VML `<wps:wsp>` 结构中，`<w:p>` 作为 `<w:r>` 的子元素出现（`<w:r><w:txbxContent><w:p>...`）。这是 OOXML 规范禁止的：`<w:r>` 不应包含 `<w:p>`。这种深层嵌套的修复需要手动调整 XML 结构。

#### 发现 4：`<w:pPr: 621/587 (diff=34)`——34 个未闭合的 `<w:pPr>`
模板中部分 `<w:pPr>` 元素未正确闭合，影响样式继承。

### 13.4 经验教训

#### 13.4.1 标签修复的三步走策略

```
Step 1: Fix <w:t>text</w:r>                   ── 粗粒度，全局搜索
Step 2: 逐段落平衡 w:r（ro vs rc）              ── 中粒度，段落级别
Step 3: 线性扫描定位游离 </w:r>（balance < 0）  ── 精粒度，字符级别
```

**必须按此顺序执行**，否则 Step 2 会在 Step 1 之前错误地添加 `</w:r>`。
